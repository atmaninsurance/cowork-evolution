## 1. What OI-000030 is trying to do

**In one sentence:** stop things that shouldn't be written down from being written down
automatically, at the one place that can actually stop it.

The longer version, as a system:

Every Claude session — Code sessions and remote Cowork chats — leaves a raw machine record of
itself. A nightly process reads those raw records and reconstructs them into readable transcript
files under `~/Claude/transcripts/`. Those files are version-controlled, and the nightly sweep
commits them and sends them to GitHub.

**Nothing in that pipeline inspects what it is copying.** If something of the gated class is
pasted into any chat — by you, by me, by an agent quoting a config file — the reconstruction
copies it verbatim into a tracked file, and the sweep sends it to a remote host.

That is not hypothetical. It happened on 2026-07-20: a bot token pasted into a build session was
reconstructed into its transcript. Three affected files were committed and sent on 07-21 before
anyone noticed. A fourth was caught the next day. You rotated the value out of band on 07-27.

Two properties make it a machinery problem rather than a hygiene problem:

- **Hand-fixing does nothing.** The transcript files are tool-owned. The exporter regenerates
  them from the raw record. Anything edited by hand comes back on the next run.
- **It grows by being observed.** Each night's end-of-day compaction reads the affected
  transcript, and by reading it produces another affected file. CLD-00076 records this as the
  reason exporter-side redaction is *"the only fix that terminates the loop."*

**What the task would build:** a shared scrub in the exporters' common library so anything of that
class is replaced with a visible marker on the way into the tracked surface, plus a matching
finding in the nightly transcript lint so a near-miss the scrub doesn't recognise shows up as an
alarm rather than as silence.

### One correction I owe you

I told you this morning that CLD-00076 was "the only live-risk item in the backlog." **That was
overstated and I should not have written it.** The item's own 07-27 entry says the opposite:

The forward risk is real — the next thing pasted lands on the same conveyor belt. But the fire is

## 2. Why the gate calls it structural

### The distinction DEC-0091 draws

DEC-0091 (2026-07-28) split the deny-listed classes into two kinds, and the split is the whole
point:

**Grantable** — service definitions, Alfred deployment work, git-history operations. Item 2's
words: *"classes whose harm is adjudicable risk, where David's recorded judgment is the missing
ingredient."* A task can't authorise itself, but you can. The orchestrator mints a grant record
into a directory tasks cannot write, the gate checks the registry, and the work proceeds headless
with full provenance in the ledger.

**Structural** — never grantable, approval or not. Three classes: the sensitive-material class,
Alfred's constitutional documents, and the authorization substrate itself. The reason, verbatim
from the decision's own summary:

> *"The structural set names the classes where harm is independent of judgment; approval cannot
> fix physics, governance, or substrate integrity, so no grant exists there."*

### The specific reasoning for this class — and this is the part worth sitting with

DEC-0091 item 2, verbatim, on why the sensitive-material class is structural:

> *"capture-leak physics: headless session JSONLs are reconstructed into git-pushed transcripts,
> so an authorized token transit leaks identically to an unauthorized one — CLD-00076;
> out-of-band installation remains the only path"*

Read that carefully. **The justification for the structural bar is the transcript capture
pipeline.** The reasoning is: a headless session's raw record becomes a tracked, remotely-stored
transcript, so it makes no difference whether the material was there with your blessing or
without it — the leak is identical either way. Approval changes the authorization; it does not
change what the recorder records.

And DEC-0091 cites **CLD-00076** by name as the rationale — the same item OI-000030 is anchored
on. The decision's Related line lists it as *"CLD-00076 (structural-credential rationale)."*

So the shape of the thing is this:

> **The class is unwaivable because of the capture pipeline. The task wants to fix the capture
> pipeline. The defect that makes the bar necessary is the defect the work would repair.**

That is not a loophole and I am not arguing it should be one. But it is the substance of the
morning conversation, because it means the bar is in some sense self-perpetuating: the one kind
of work that would reduce capture-leak physics is work that capture-leak physics forbids doing
unattended.

### How it is actually enforced

Not by convention — by code, in three places:

1. **`_meta/screen.py:204`** defines the structural set. The comment above it: *"never grantable,
   approval or not — capture-leak physics, joint-review governance, and the authorization
   substrate itself. Hard-coded here, checked before any registry lookup, in EVERY mode."*
2. **`_meta/screen.py:404`**, inside the shared deny pass used by *both* screens. On a match it
   looks up the class, and if the class is structural it records the rejection and `continue`s —
   **before the grant-registry lookup is ever reached.** Its own reject text: *"STRUCTURAL class
   … never grantable (DEC-0091 item 2); no grant, declaration, or origin waives it."*
3. **`_meta/screen.py:276`** makes *declaring* the capability an error in itself: *"declaring it
   cannot make it waivable."* And any declaration error suppresses every waiver on the file.

There is no path through. Not a grant, not a trusted origin, not your explicit approval typed
into the document.

### The precedent, on this exact item

**OI-000009**, 2026-07-28. Minted 08:05, screen-rejected 08:05, disposed the same minute. The
ledger line names the matched class and disposes it. What happened instead, from CLD-00076

> *"The intake was minted (OI-000009) and hard-rejected at the intake screen by design (deny-list
> matched the domain vocabulary — the OI-000004 structural bar: secret-handling work never routes
> headless). Executed supervised in-chat instead (`remote_c209d02d`, DEC-0081 exception)."*

It worked. The supervised sitting diagnosed a subtler root cause than the intake had assumed, and

## 3. The governance question — question 2

This is the one I'd most want your thinking on, because it is a finding about the rules
themselves rather than about this task.

**What happened:** my intake for OI-000030 passed the mechanical screen with **zero deny hits.**
Not because the work is safe — the work sits squarely in a structural class — but because I
followed the authoring contract's §2 rule and wrote at class level, describing the category
instead of using its vocabulary. The gate is a set of text patterns. I gave it no text to match.

**Why that rule exists:** it was written *because of OI-000009.* DEC-0091 item 6 names it as the
source datapoint — intakes should be worded at class level *"so the mechanical screen doesn't
false-positive on its own subject matter."* OI-000009 tripped the gate merely by talking about
the class, and that was a genuine nuisance worth fixing.

**The consequence nobody traced:** the rule written to stop the gate from catching *harmless*
mentions also lets *genuinely structural work* walk past untouched. OI-000009 was caught because
it was worded naively. Mine was not caught because it was worded correctly. The structural bar —
the one thing in this system that admits no exception — is currently enforced by an author's
word choice.

V/D put it as: *"the structural bar is currently enforced by an author's word choice rather than
by the gate."*

**What it proposed, as a question rather than a fix:** should the screen gain a positive
*intent-based* detector for work of this kind — something that recognises "this task is about
scrubbing that class" regardless of vocabulary — and should the authoring contract forbid
class-level wording when the work itself sits in a structural class?

**My own read, offered as a view rather than a recommendation:** the second half is the cheap and
obviously-correct half — a rule that says *if the work is in a structural class, say so plainly
and expect to be stopped* costs nothing and closes the specific hole. The first half is harder
and I'd want to think before advocating it: an intent detector is a semantic judgment living
inside a deliberately mechanical gate, and DEC-0091 item 1 is explicit that the semantic half
belongs with V/D, where prose belongs — *"the last gate never reads prose."* Notably, **V/D did
catch it.** The layered design worked. What failed was only the outer, mechanical layer, which
was never meant to carry semantic weight.

This looks DEC-worthy to me. Say the word and I'll capture it.
